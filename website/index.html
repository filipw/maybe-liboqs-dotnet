A .NET wrapper for liboqs

Post-quantum cryptography, available from .NET

Maybe LibOQS.NET exposes the quantum-resistant key encapsulation mechanisms and digital signature schemes implemented by liboqs to .NET applications, with the native library bundled so that no separate compilation step is required.

Wraps liboqs 0.16.0 Runtime .NET 9.0 or later Licence MIT Platforms Windows, Linux, macOS

This is an independent project. It is not affiliated with, nor endorsed by, the Open Quantum Safe project. It packages and links against liboqs, which performs all of the underlying cryptographic work and is distributed under its own licence. The acknowledgements section below records this dependency in full.

Section 1

Overview

Maybe LibOQS.NET is a binding layer. It does not implement cryptography itself. Instead it forwards calls to liboqs, the C library maintained by the Open Quantum Safe project, and presents the results through an idiomatic .NET surface. The intent is to make the algorithms that are currently being standardised by NIST reachable from C# without obliging the caller to build a native toolchain.

The project ships as two packages. LibOQS.NET.Native contains the low-level P/Invoke declarations and the platform-specific native binaries. LibOQS.NET builds on top of it and offers a typed API with enumerations for the algorithms and disposable handles for the underlying native state. Both packages carry the native dependencies for every supported platform, so adding a package reference is sufficient.

Section 2

Why post-quantum cryptography

The public-key cryptography in widespread use today, including RSA and elliptic-curve schemes, rests on mathematical problems that a sufficiently large quantum computer could solve efficiently using Shor's algorithm. No such machine exists at present, but encrypted material that is recorded now could be retained and decrypted later. This prospect motivates a transition to schemes whose security is believed to hold against quantum as well as classical adversaries.

Two families of primitive cover most needs. A key encapsulation mechanism allows two parties to agree on a shared secret over an insecure channel: one party publishes a public key, the other uses it to produce a ciphertext and a secret, and the first party recovers the same secret from the ciphertext. A digital signature scheme lets a holder of a private key produce a signature over a message that anyone holding the corresponding public key can verify, and that cannot be forged without the private key.

In 2024 NIST published the first finalised standards in this area: ML-KEM for key encapsulation, derived from CRYSTALS-Kyber, and ML-DSA and SLH-DSA for signatures, derived from CRYSTALS-Dilithium and SPHINCS+ respectively. liboqs implements these alongside a wider set of candidates from the ongoing standardisation effort, and Maybe LibOQS.NET makes that set available to .NET callers.

Terminology. Throughout this site, the name printed for an algorithm is the identifier used by liboqs, for example ML-KEM-768 or ML-DSA-65. The numeric suffix indicates the parameter set, which fixes the key sizes and the claimed security level.

Section 3

Getting started

Add a reference to the high-level package. Nothing else is required: the native libraries for each supported platform travel with the package, and the library initialises itself on first use.

Project file
<PackageReference Include="LibOQS.NET" Version="..." />

Or from the command line:

Shell
dotnet add package LibOQS.NET

The following program exercises both primitives. It encapsulates and recovers a shared secret with ML-KEM-512, then signs and verifies a message with ML-DSA-44. The using declarations ensure that the native handles are released when each instance leaves scope.

C#
using LibOQS.NET;

// The library initialises automatically; no explicit Initialize() call is needed.

// Key encapsulation with ML-KEM-512
using var kem = new KemInstance(KemAlgorithm.MlKem512);
var (publicKey, secretKey) = kem.GenerateKeypair();
var (ciphertext, sharedSecret1) = kem.Encapsulate(publicKey);
var sharedSecret2 = kem.Decapsulate(secretKey, ciphertext);
Console.WriteLine($"Shared secrets match: {sharedSecret1.SequenceEqual(sharedSecret2)}");

// Digital signature with ML-DSA-44
using var sig = new SigInstance(SigAlgorithm.MlDsa44);
var (sigPublicKey, sigSecretKey) = sig.GenerateKeypair();

var message = System.Text.Encoding.UTF8.GetBytes("Hello, post-quantum world!");
var signature = sig.Sign(message, sigSecretKey);
var isValid = sig.Verify(message, signature, sigPublicKey);
Console.WriteLine($"Signature valid: {isValid}");
Checking availability. A given build of liboqs need not enable every algorithm. Before constructing an instance you can query KemAlgorithm.MlKem512.IsEnabled() or the equivalent on a signature algorithm, and fall back to another parameter set if necessary.
Section 4

Demonstrations

The examples that follow are taken from the sample console application in the repository. They are reproduced here as source so that the shape of the API is visible without running anything. Because the library wraps a native component, it executes on the .NET runtime rather than in the browser, so these listings are for reading rather than live execution.

Section 4.1

Key encapsulation

The exchange has three steps. The receiver, here named Alice, generates a key pair and publishes the public key. The sender, Bob, encapsulates a fresh shared secret against that public key, which yields a ciphertext and the secret. Alice then decapsulates the ciphertext with her secret key and arrives at the same shared secret.

C# / ML-KEM
using var kem = new KemInstance(KemAlgorithm.MlKem768);

// Alice generates a key pair and publishes the public key.
var (alicePublicKey, aliceSecretKey) = kem.GenerateKeypair();

// Bob encapsulates a shared secret against Alice's public key.
var (ciphertext, bobSharedSecret) = kem.Encapsulate(alicePublicKey);

// Alice decapsulates the ciphertext with her secret key.
var aliceSharedSecret = kem.Decapsulate(aliceSecretKey, ciphertext);

// Both parties now hold the same secret.
var equal = bobSharedSecret.SequenceEqual(aliceSharedSecret);
Console.WriteLine($"Shared secrets match: {equal}");

The instance also reports the sizes that the chosen parameter set requires, through PublicKeyLength, SecretKeyLength, CiphertextLength and SharedSecretLength. These are useful when allocating storage or when presenting the parameters of a scheme.

Section 4.2

Digital signatures

A signature scheme follows a similar pattern. The signer generates a key pair, signs a message with the secret key, and any party holding the public key can verify the result. Altering the message after signing causes verification to fail, which the listing below demonstrates with a deliberately tampered copy.

C# / ML-DSA
using System.Text;

using var sig = new SigInstance(SigAlgorithm.MlDsa65);

var message = Encoding.UTF8.GetBytes("Hello, ML-DSA from LibOQS.NET!");

// Generate a key pair and sign the message.
var (publicKey, secretKey) = sig.GenerateKeypair();
var signature = sig.Sign(message, secretKey);

// Verification succeeds for the original message.
var verified = sig.Verify(message, signature, publicKey);
Console.WriteLine($"Signature verified: {verified}");

// Verification fails once the message is altered.
var tampered = Encoding.UTF8.GetBytes("Hello, ML-DSA from LibOQS.NET? (tampered)");
var tamperedVerified = sig.Verify(tampered, signature, publicKey);
Console.WriteLine($"Tampered verification: {tamperedVerified}"); // expected: false
Section 4.3

Signed key exchange

Key encapsulation establishes a shared secret but says nothing about who the other party is. Combining it with signatures addresses that. Each party holds a long-term signature key pair. The key encapsulation material is signed before it is sent, so that the recipient can confirm its origin before acting on it. The example below uses ML-DSA-44 for the signatures and ML-KEM-512 for the encapsulation.

C# / Signed exchange
using var sigAlg = new SigInstance(SigAlgorithm.MlDsa44);
using var kemAlg = new KemInstance(KemAlgorithm.MlKem512);

// Long-term signature keys for both parties.
var (aSigPk, aSigSk) = sigAlg.GenerateKeypair();
var (bSigPk, bSigSk) = sigAlg.GenerateKeypair();

// Alice sends a KEM public key, signed with her long-term key.
var (kemPk, kemSk) = kemAlg.GenerateKeypair();
var signature1 = sigAlg.Sign(kemPk, aSigSk);

// Bob verifies Alice's signature before encapsulating.
if (!sigAlg.Verify(kemPk, signature1, aSigPk))
    throw new Exception("Failed to verify Alice's signature");

var (kemCt, bKemSs) = kemAlg.Encapsulate(kemPk);
var signature2 = sigAlg.Sign(kemCt, bSigSk);

// Alice verifies Bob's signature, then decapsulates.
if (!sigAlg.Verify(kemCt, signature2, bSigPk))
    throw new Exception("Failed to verify Bob's signature");

var aKemSs = kemAlg.Decapsulate(kemSk, kemCt);

// Both parties now share an authenticated secret.
Console.WriteLine($"Key exchange successful: {aKemSs.SequenceEqual(bKemSs)}");

The exchange shown here is a teaching example. A deployed protocol would also bind the identities, fix the message formats, and guard against replay. The point of the listing is to show how the two primitives compose, not to specify a protocol.

Section 5

Three ways to reach these algorithms from .NET

Maybe LibOQS.NET is one of several routes to post-quantum cryptography on .NET, and it is worth understanding where it sits. The comparison below is drawn from a companion set of samples that exercises the same operations through three libraries: the algorithms built into .NET, the managed BouncyCastle library, and this wrapper.

.NET System API

System.Security.Cryptography

The official surface, introduced in .NET 10. It is the natural choice where it is available, but it requires a recent Windows build or OpenSSL 3.5 on Linux, is not offered on macOS, and some of its types are still marked experimental.

Fully managed

BouncyCastle

A pure-managed library targeting .NET Standard 2.0. It runs everywhere the runtime runs, including macOS and WebAssembly, which makes it the most portable option, and it covers a sizeable set of schemes.

Native wrapper

Maybe LibOQS.NET

A wrapper over the liboqs C library. It exposes the broadest set of parameter sets of the three, and runs on the desktop and server platforms, but because it depends on native code it does not target WebAssembly.

The same ML-KEM exchange written against each library shows how the surfaces differ in shape while performing the same work.

System.Security.Cryptography

C#
using System.Security.Cryptography;

using var aliceKeyPair = MLKem.GenerateKey(MLKemAlgorithm.MLKem768);
var publicKey = aliceKeyPair.ExportEncapsulationKey();

using var bobKey = MLKem.ImportEncapsulationKey(MLKemAlgorithm.MLKem768, publicKey);
bobKey.Encapsulate(out byte[] ciphertext, out byte[] bobSecret);

byte[] aliceSecret = aliceKeyPair.Decapsulate(ciphertext);
Console.WriteLine($"Secrets equal: {bobSecret.SequenceEqual(aliceSecret)}");

BouncyCastle

C#
using Org.BouncyCastle.Crypto.Kems;
using Org.BouncyCastle.Crypto.Parameters;
using Org.BouncyCastle.Security;

var random = new SecureRandom();
var generator = new MLKemKeyPairGenerator();
generator.Init(new MLKemKeyGenerationParameters(random, MLKemParameters.ml_kem_768));
var aliceKeyPair = generator.GenerateKeyPair();

var encapsulator = new MLKemEncapsulator(MLKemParameters.ml_kem_768);
encapsulator.Init(new ParametersWithRandom(aliceKeyPair.Public, random));
var ciphertext = new byte[encapsulator.EncapsulationLength];
var bobSecret = new byte[encapsulator.SecretLength];
encapsulator.Encapsulate(ciphertext, 0, ciphertext.Length, bobSecret, 0, bobSecret.Length);

var decapsulator = new MLKemDecapsulator(MLKemParameters.ml_kem_768);
decapsulator.Init(aliceKeyPair.Private);
var aliceSecret = new byte[decapsulator.SecretLength];
decapsulator.Decapsulate(ciphertext, 0, ciphertext.Length, aliceSecret, 0, aliceSecret.Length);

Maybe LibOQS.NET

C#
using LibOQS.NET;

using var kem = new KemInstance(KemAlgorithm.MlKem768);
var (alicePublic, alicePrivate) = kem.GenerateKeypair();
var (ciphertext, bobSecret) = kem.Encapsulate(alicePublic);
var aliceSecret = kem.Decapsulate(alicePrivate, ciphertext);
Console.WriteLine($"Secrets equal: {bobSecret.SequenceEqual(aliceSecret)}");

Section 7

Supported algorithms

The library exposes the key encapsulation and signature families that liboqs provides, across their standard parameter sets. The headline schemes are the NIST standards, ML-KEM for key encapsulation and ML-DSA together with SLH-DSA for signatures. Beyond these, the library also surfaces a range of further candidates, including lattice, code-based and multivariate constructions, for evaluation and comparison.

  • Key encapsulation: ML-KEM and Kyber, the code-based BIKE, HQC and Classic McEliece, the NTRU and NTRU Prime families, and FrodoKEM in both its standard and ephemeral forms.
  • Signatures: ML-DSA and SLH-DSA, the lattice-based Falcon, and the multivariate and code-based MAYO, CROSS, UOV, SNOVA and MQOM families.

The full enumeration of parameter sets, with the security level associated with each, is set out on a dedicated page.

Section 8

Platform support

The packages include native binaries for the following targets, and require no further setup on any of them.

  • Windows x64 and Windows ARM64
  • Linux x64 and Linux ARM64
  • macOS ARM64
Known limitations on Windows. The pure SLH-DSA variants are disabled on Windows because a defect in liboqs causes a stack overflow during signing. BIKE is unavailable because liboqs itself does not support it on Windows. Both remain available on the other supported platforms.
MQOM. The MQOM family is available on every supported platform. On Windows and macOS it is built from the memory-optimised implementation introduced in liboqs 0.16.0, because the default implementation requires more than 1 MB of stack to sign and so overflows the stack of non-main threads. On Linux the default implementation is used, which is AVX2-accelerated on x64.
Section 9

Resource management

The library holds native state on behalf of each KemInstance and SigInstance. Both implement IDisposable, so the recommended practice is to wrap them in using declarations, as the examples above do, which releases the native handles deterministically when they leave scope.

Initialisation happens automatically the first time the library is used, and that path is safe to call from multiple threads. Disposal is idempotent and may be called concurrently; an instance that is never disposed is still released by the handle's critical finaliser. For the algorithm instances themselves, the recommendation is to use a separate instance per thread rather than sharing one. An optional LibOqs.Cleanup() call is available for releasing library-wide resources, and should be made only after every instance has been disposed. It is not invoked automatically at process exit.

Key material is not erased for you. Keys and shared secrets are returned as ordinary managed byte[]. The garbage collector may move or copy those arrays and nothing zeroes them once they fall out of scope, so the library cannot guarantee secrets are cleared from process memory. Where that matters, clear the arrays yourself once finished with them.
